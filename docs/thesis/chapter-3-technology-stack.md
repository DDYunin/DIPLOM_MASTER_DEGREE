## Введение к главе 3

Клиентская часть платформы для обучения студентов представляет собой одностраничное приложение (SPA), обеспечивающее работу трёх категорий пользователей — администратора, преподавателя и студента. Для реализации интерфейса, управления данными, маршрутизации и сопровождения жизненного цикла разработки был сформирован программный стек на базе экосистемы Vue 3.

Цель настоящей главы — систематизировать и обосновать выбор технологий, использованных при создании frontend-части системы. Материал главы организован по функциональным блокам: платформа сборки, ядро приложения, управление состоянием и навигация, построение интерфейса, работа с данными и формами, инструменты качества кода, а также окружение разработки и развёртывания.

Описание каждой технологии строится по единому шаблону:

1. **Назначение** — краткая характеристика инструмента и его роли в современной frontend-разработке.
2. **Решаемые проблемы** — какие задачи проекта обусловили необходимость его применения.
3. **Обоснование выбора** — сравнение с рассмотренными альтернативами и аргументы в пользу принятого решения.
4. **Применение в проекте** — конкретные места использования в кодовой базе (модули, сценарии, команды).
5. **Иллюстрации** (при необходимости) — схемы, таблицы или скриншоты, поясняющие интеграцию инструмента.

Сводная характеристика всего стека приведена в таблице 3.1 в конце главы. **Рисунки и схемы к главе** — в файле [`chapter-3-diagrams.md`](./chapter-3-diagrams.md). Архитектурная организация исходного кода (Feature-Sliced Design) рассмотрена в отдельной главе и здесь упоминается только там, где это необходимо для понимания контекста применения технологий.

## Сравнительный анализ frontend-фреймворков

Выбор базового UI-фреймворка — ключевое архитектурное решение, определяющее структуру компонентов, экосистему библиотек и подход к управлению состоянием. Для проекта учебной платформы рассматривались три распространённых решения: **Vue 3**, **React** и **Angular**.

**Таблица 3.2** — Сравнительная характеристика frontend-фреймворков

| Критерий                 | Vue 3                    | React                       | Angular                             |
| ------------------------ | ------------------------ | --------------------------- | ----------------------------------- |
| Тип                      | Прогрессивный фреймворк  | Библиотека для UI           | Полнофункциональный фреймворк       |
| Язык шаблонов            | SFC (HTML + CSS + JS/TS) | JSX/TSX                     | HTML-шаблоны + TypeScript           |
| Кривая обучения          | Умеренная                | Умеренная–высокая           | Высокая                             |
| Встроенная маршрутизация | Vue Router (официальный) | React Router (сторонний)    | Angular Router (встроенный)         |
| Управление состоянием    | Pinia (официальный)      | Redux, Zustand, Jotai и др. | NgRx, Signals                       |
| Размер экосистемы        | Большая                  | Наибольшая                  | Большая, enterprise-ориентированная |
| TypeScript               | Полная поддержка         | Полная поддержка            | TypeScript «из коробки»             |
| Подход к реактивности    | Proxy-based reactivity   | Virtual DOM, hooks          | Change Detection, Signals           |
| Типичная сборка          | Vite                     | Vite / Webpack              | Angular CLI                         |
| SSR / meta-фреймворки    | Nuxt                     | Next.js                     | Angular Universal                   |

**Vue 3** сочетает декларативные шаблоны, высокую производительность за счёт fine-grained reactivity и относительно низкий порог входа. Composition API позволяет организовывать логику так же гибко, как React Hooks, сохраняя при этом читаемость шаблонов для UI-heavy приложений (формы, таблицы, модальные окна).

**React** обладает наибольшим сообществом и рынком готовых решений, однако требует явного выбора и интеграции маршрутизации, форм, UI-kit и state management. Для SPA учебной платформы без SSR это не давало существенных преимуществ при более фрагментированной экосистеме «из коробки».

**Angular** предоставляет цельную enterprise-платформу, но избыточен для клиентского SPA средней сложности: более высокий порог входа, verbose-конфигурация, больший overhead для команды из одного–двух разработчиков.

**Вывод.** Vue 3 выбран как оптимальный баланс между продуктивностью разработки, согласованностью официальной экосистемы (Router, Pinia, Vue I18n) и соответствием масштабу проекта — SPA с тремя ролевыми порталами без необходимости SSR. См. **рисунок 3.18**.

## П. 3.13 Husky (актуальная реализация в проекте)

**Husky** — инструмент настройки Git hooks. **lint-staged** запускает проверки только для файлов, попавших в индекс commit.

**Применение в проекте.** Скрипт `prepare` в `package.json` активирует Husky при `npm install`. Hook `.husky/pre-commit` выполняет `lint-staged`: для `*.{vue,ts,tsx,mts}` — oxlint, eslint и prettier; для `*.{json,css,md}` — prettier. Hook `.husky/pre-push` запускает `npm run test:run` (unit-тесты).

## П. 3.14 JSON Server — локальный mock API

### Назначение

**JSON Server** — утилита для быстрого развёртывания REST API поверх файла JSON. Она интерпретирует коллекции в `db.json` как ресурсы (`/users`, `/courses` и т.д.) и автоматически поддерживает операции **GET, POST, PUT, PATCH, DELETE**, а также фильтрацию и пагинацию через query-параметры.

По сути JSON Server — это лёгкий HTTP-сервер с «фейковой» базой данных, удобной для прототипирования и параллельной разработки клиента и сервера.

### Решаемые проблемы

На ранних этапах создания клиентской части платформы полноценный бэкенд (микросервисы пользователей, курсов, файлов) может быть недоступен, нестабилен или реализован частично. При этом frontend уже должен:

- отображать списки пользователей, курсов, организационную иерархию;
- обрабатывать формы создания и редактирования (POST/PATCH);
- отрабатывать сценарии авторизации и обработки ошибок сети.

Без mock API разработчик вынужден либо «зашивать» данные в компоненты, либо писать объёмный перехватчик запросов внутри клиентского кода. Оба подхода усложняют поддержку и не соответствуют реальному HTTP-взаимодействию.

JSON Server выносит mock-данные в **отдельный процесс**, что позволяет frontend работать с тем же `fetch`/TanStack Query, что и в production, меняя только адрес API через proxy Vite.

### Обоснование выбора

| Критерий                 | JSON Server                     | MSW (Mock Service Worker) | Mock в коде клиента        |
| ------------------------ | ------------------------------- | ------------------------- | -------------------------- |
| Где выполняется mock     | Отдельный Node.js-процесс       | Service Worker в браузере | Внутри `apiClient`         |
| REST из коробки          | Да                              | Нужно описывать handlers  | Нужно писать вручную       |
| Редактирование данных    | `db.json` + сохранение при POST | In-memory в handlers      | In-memory в коде           |
| Близость к реальному API | Высокая (настоящий HTTP)        | Высокая                   | Средняя                    |
| Сложность настройки      | Низкая                          | Средняя                   | Растёт с числом эндпоинтов |

**MSW** удобен для тестов и изоляции компонентов, но для ежедневной разработки экранов с десятками эндпоинтов JSON Server проще сопровождать: достаточно обновить JSON-файл.

**Mock в коде клиента** (перехват в `apiClient`) смешивает инфраструктуру и бизнес-слой, увеличивает размер бандла и усложняет переключение на реальный бэкенд.

**Вывод:** JSON Server выбран как основной инструмент локального mock API на этапе разработки frontend.

### Применение в проекте

Структура mock-окружения:

```
mock/json-server/
  db.json        — коллекции данных (пользователи, курсы, иерархия вуза)
  routes.json    — сопоставление URL API и ресурсов db
  server.cjs     — расширения: auth/login, PageResponse, задержка сети
```

**Запуск mock-сервера:**

```bash
npm run mock:server
```

Сервер поднимается на порту **3001**. Данные первоначально подготовлены на основе файлов `public/mock-data/` и дополняются по мере появления новых эндпоинтов.

**Интеграция с Vite.** В режиме разработки dev-сервер Vite проксирует запросы с префиксом `/api` на JSON Server (аналогично проксированию на реальные микросервисы в production). Frontend использует единый `apiClient` и маршруты `usersApiPath`, `courseApiPath` — меняется только целевой хост proxy, а не код сущностей.

**Кастомизация.** Стандартного поведения JSON Server недостаточно для:

- эндпоинта `POST /auth/login` (возврат mock JWT);
- ответа списка пользователей в формате `PageResponse` (`items`, `totalElements`, …);
- имитации сетевой задержки (~300 ms).

Эти сценарии реализованы в `server.cjs` поверх базового router JSON Server.

**Переход на реальный бэкенд.** После готовности микросервисов в `vite.config.ts` proxy перенаправляется на фактические хосты (`users`, `course`, `files`). Mock-сервер отключается, код слоёв `entities` остаётся без изменений — меняется только транспортный уровень.
