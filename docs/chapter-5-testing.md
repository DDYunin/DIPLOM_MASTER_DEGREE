## Введение к главе 5

Разработка клиентской части образовательной платформы сопровождается комплексом мер, обеспечивающих качество программного кода на протяжении всего жизненного цикла продукта. В академической литературе принято разграничивать понятия верификации (verification) и валидации (validation): верификация отвечает на вопрос «правильно ли построена система?», тогда как валидация — «правильная ли система построена?» [ссылка]. Настоящая глава охватывает оба аспекта: от автоматической проверки синтаксиса и стиля до компонентных тестов и изолированной документации.

Цель главы — описать выбранную стратегию тестирования и автоматизации, обосновать применение каждого инструмента и привести конкретные результаты, полученные в рамках разработки платформы. Материал организован по уровням тестовой пирамиды [Beck, 2002]: от статического анализа и модульных тестов к компонентным. Дополнительно рассматривается изолированная среда разработки компонентов Storybook, которая совмещает функции документирования и тестирования.

Разграничение уровней тестирования иллюстрирует **рисунок 5.1** — адаптированная тестовая пирамида применительно к стеку проекта.

## 5.1 Организация автоматических проверок качества кода с использованием Git-хуков

### 5.1.1 Назначение и место в процессе разработки

Первой линией защиты качества кода в проекте является статический анализ — автоматическая проверка исходного кода без его выполнения. Статический анализ выявляет синтаксические ошибки, нарушения принятого стиля оформления и потенциально ошибочные конструкции ещё на этапе редактирования или перед фиксацией изменений в репозитории.

В отличие от юнит-тестов, инструменты статического анализа работают с исходным текстом и не требуют запуска приложения. Это делает их принципиально более быстрыми: полный цикл проверки занимает секунды, а не минуты. Ранее обнаруженная проблема обходится значительно дешевле, чем дефект, найденный на стадии тестирования — данный принцип известен как «shift left» [ссылка].

В рамках проекта статический анализ реализован тремя инструментами:

- **ESLint** с плагинами для Vue 3 и TypeScript — анализирует семантику кода и специфические антипаттерны Vue-компонентов;
- **Oxlint** — высокопроизводительный линтер, реализованный на Rust, обеспечивающий быструю первичную проверку правил корректности;
- **Prettier** — форматтер, обеспечивающий единообразное оформление кода вне зависимости от среды разработки конкретного участника команды.

Чтобы гарантировать запуск проверок на каждое изменение кодовой базы, используется механизм **Git-хуков**, автоматизированный через инструмент **Husky**.

### 5.1.2 Git-хуки, Husky и lint-staged

**Git-хук** — скрипт, который Git автоматически вызывает в ответ на определённые события: создание коммита, отправку изменений на сервер и другие. Если скрипт завершается с ненулевым кодом, соответствующее Git-действие прерывается.

Традиционная проблема хуков — их нахождение внутри директории `.git/`, которая не отслеживается системой контроля версий. **Husky** решает эту проблему: инструмент перенаправляет хуки в директорию `.husky/`, которая фиксируется в репозитории наравне с остальным кодом. При выполнении `npm install` скрипт `prepare` автоматически инициализирует Husky, после чего хуки становятся доступны всем участникам без дополнительных действий.

В проекте настроены два хука. **`.husky/pre-commit`** делегирует работу инструменту `lint-staged`, который запускает проверки только для файлов, добавленных в индекс Git (staged files) — это исключает прогон всей кодовой базы при каждом коммите. **`.husky/pre-push`** выполняет полный прогон модульных тестов командой `npm run test:run` перед отправкой ветки в удалённый репозиторий.

Конфигурация `lint-staged` задаётся в `package.json`:

```json
"lint-staged": {
  "*.{vue,ts,tsx,mts}": [
    "oxlint --fix",
    "eslint --fix --cache",
    "prettier --write --experimental-cli"
  ],
  "*.{json,css,md}": [
    "prettier --write --experimental-cli"
  ]
}
```

Для Vue- и TypeScript-файлов применяется последовательная цепочка: Oxlint выполняет быстрый первичный проход (~1–2 мс на файл), ESLint проводит семантический анализ с учётом специфики Vue 3, Prettier финально форматирует результат. Порядок инструментов принципиален: ESLint исправляет логику до форматирования.

ESLint настроен в формате Flat Config (файл `eslint.config.ts`, ESLint v9). Слой `pluginOxlint.buildFromOxlintConfigFile` синхронизирует конфигурации двух линтеров, исключая двойную проверку одних и тех же правил. Слой `skipFormatting` (из `eslint-config-prettier`) делегирует всё форматирование Prettier.

Разделение проверок между хуками обосновано разницей в частоте и стоимости:

| Событие      | Хук          | Команда       | Типичное время | Цель                            |
| ------------ | ------------ | ------------- | -------------- | ------------------------------- |
| `git commit` | `pre-commit` | `lint-staged` | 2–5 с          | Стиль и синтаксис staged-файлов |
| `git push`   | `pre-push`   | `vitest run`  | 15–30 с        | Корректность бизнес-логики      |

### 5.1.3 Результаты

Интеграция Husky, lint-staged и линтеров обеспечивает следующие измеримые эффекты:

- **Автоматическое исправление** распространённых нарушений (`--fix`) снижает ручную работу разработчика по приведению кода к стандарту.
- **Блокировка коммита** при наличии неисправимых ошибок ESLint или Oxlint исключает попадание некорректного кода в историю репозитория.
- **Единый стиль** кодовой базы гарантируется Prettier — форматирование становится детерминированным вне зависимости от настроек IDE.
- **Быстрая обратная связь**: среднее время выполнения `pre-commit` хука составляет 3–4 секунды для типичного коммита из 3–5 изменённых файлов.

## 5.2 Модульное и интеграционное тестирование бизнес-логики с использованием Vitest

### 5.2.1 Назначение и выбор инструмента

Второй уровень тестовой пирамиды занимают **модульные (unit) тесты** — автоматические проверки небольших, изолированных фрагментов кода: отдельных функций, сервисов, Zod-схем и компонентов. В отличие от E2E-тестов, которые проверяют пользовательский сценарий целиком, модульные тесты локализуют источник проблемы: падение конкретного теста немедленно указывает на конкретную функцию или ветку логики.

Для запуска тестов выбран **Vitest** — тест-раннер, построенный на базе Vite. Его ключевые преимущества в контексте проекта:

- **Общий pipeline с Vite**: Vitest использует ту же конфигурацию плагинов и алиасов (`@/` → `src/`), исключая необходимость поддерживать отдельный конфиг трансформации TypeScript.
- **Нативная поддержка ESM и TypeScript**: работает без дополнительных пресетов трансформации.
- **Встроенный spy/mock API**: `vi.fn()`, `vi.stubGlobal()`, `vi.mock()` полностью совместимы с Jest по интерфейсу.

### 5.2.2 Конфигурация и структура тестов

Vitest использует концепцию **projects** — логически изолированных конфигураций внутри одного `vitest.config.ts`. В проекте определено два проекта: `unit` для модульных тестов и `storybook` для interaction-тестов Storybook (рассматривается в п. 5.3). Ключевые параметры проекта `unit`:

```typescript
{
  test: {
    name: 'unit',
    environment: 'happy-dom',
    setupFiles: ['./src/test/setup.ts'],
    include: ['src/**/*.{spec,test}.{ts,tsx}'],
    clearMocks: true,
    restoreMocks: true,
  }
}
```

**Happy-DOM** выбран как тестовая среда — реализация DOM API на чистом JavaScript, значительно быстрее JSDOM. Глобальный файл `src/test/setup.ts` сбрасывает `localStorage` перед каждым тестом и после него, обеспечивая изоляцию состояния между тест-кейсами.

### 5.2.3 Тесты чистых функций и хелперов

Наиболее изолированный уровень — тесты чистых функций без побочных эффектов. JWT-токен в проекте хранит поле `exp` — время истечения в формате Unix timestamp. Функции `isAccessTokenExpired()` и `isAccessTokenExpiringSoon(threshold)` используются в перехватчике запросов для принятия решения о необходимости обновления токена.

В тестах применяется вспомогательная фабрика `createTokenWithExp(exp)`, которая конструирует минимальный JWT с заданным `exp`. Это позволяет тестировать временну́ю логику детерминированно, не зависея от реального времени:

```typescript
it('detects token that will expire soon', () => {
  tokenService.setTokens(createTokenWithExp(Math.floor(Date.now() / 1000) + 30))

  expect(isAccessTokenExpired()).toBe(false)
  expect(isAccessTokenExpiringSoon(60)).toBe(true) // истекает через 30 с, порог — 60 с
})
```

### 5.2.4 Интеграционные тесты с мокированием fetch

Файл `auth-interceptor.spec.ts` демонстрирует **интеграционный** уровень тестирования — проверку взаимодействия нескольких модулей: функции `refreshAccessToken`, сервиса `tokenService` и обработчика истёкшей сессии.

Тест заменяет глобальный `fetch` на мок с помощью `vi.stubGlobal()`, избегая реальных HTTP-запросов. Особого внимания заслуживает тест дедупликации параллельных запросов на обновление токена: несколько запросов могут одновременно получить ответ 401. Тест гарантирует, что логика pending-промиса корректно ограничивает количество вызовов `/auth/refresh` до одного:

```typescript
it('deduplicates concurrent refresh requests', async () => {
  const [first, second] = await Promise.all([refreshAccessToken(), refreshAccessToken()])

  expect(first).toBe('new-access-token')
  expect(second).toBe('new-access-token')
  expect(fetch).toHaveBeenCalledTimes(1) // ровно один HTTP-запрос
})
```

### 5.2.5 Тесты DTO-маппер, билдеров и Zod-схем

В проекте принят паттерн **фабрики тестовых данных** — функция `createDto(overrides)`, возвращающая объект с разумными значениями по умолчанию и возможностью переопределить нужные поля. Такой подход делает тесты декларативными и снижает объём кода при добавлении новых полей в DTO — изменение вносится только в фабрику.

Тест приоритизации ролей проверяет инвариант, важный для отображения интерфейса: если пользователь имеет несколько ролей одновременно, маппер должен вернуть наивысшую:

```typescript
it('resolves primary role by priority when multiple roles are present', () => {
  const teacherUser = mapAdminUserListItemToUser(
    createDto({ roles: [ROLES.STUDENT, ROLES.TEACHER] })
  )
  expect(teacherUser.role).toBe('Teacher')
})
```

Zod-схемы задают контракт для данных формы. Тесты схем верифицируют контракт через метод `safeParse()`. Пример теста условно-обязательного поля:

```typescript
it('requires department for teacher', () => {
  const result = schema.safeParse({
    ...validBase,
    role: ROLES.TEACHER,
    departmentId: null
  })

  expect(result.success).toBe(false)
  expect(result.error.issues.some((i) => i.path[0] === 'departmentId')).toBe(true)
})
```

Поскольку схемы — чистые объекты Zod без зависимости от Vue или DOM, тест-кейс выполняется за 2–5 мс, что позволяет покрывать большое число граничных случаев без значимых потерь во времени.

### 5.2.6 Компонентные тесты с renderWithApp

Монтирование компонентов в тестах требует обеспечить тот же набор глобальных провайдеров, что и в реальном приложении: `vue-i18n`, `VueQueryPlugin` и `PrimeVue`. Для этого в проекте создана вспомогательная функция `renderWithApp`:

```typescript
export const renderWithApp = <C extends Component>(
  component: C,
  options: MountingOptions<InstanceType<C>> = {}
): VueWrapper<InstanceType<C>> => {
  const queryClient = createTestQueryClient() // retry: false, gcTime: 0

  return mount(component, {
    ...options,
    global: {
      ...options.global,
      plugins: [
        i18n,
        [VueQueryPlugin, { queryClient }],
        [PrimeVue, { theme: primeVueThemeConfig }],
        ...(options.global?.plugins ?? [])
      ]
    }
  })
}
```

`QueryClient` создаётся с отключёнными повторными запросами (`retry: false`) и нулевым временем кэширования (`gcTime: 0`). Компонентный тест `AddUserForm.spec.ts` мокирует API-зависимости через `vi.mock()` и использует `flushPromises()` из `@vue/test-utils` для ожидания разрешения всех промисов после монтирования:

```typescript
it('hides department and group fields for admin role', async () => {
  const wrapper = mountForm()
  await flushPromises()

  await setSelectValue(wrapper, '#role', ROLES.ADMIN)
  await flushPromises()

  expect(wrapper.find('#group').exists()).toBe(false)
  expect(wrapper.find('#department').exists()).toBe(false)
})
```

## 5.3 Документирование и изолированная разработка компонентов в среде Storybook

### 5.3.1 Назначение и концепция

Разработка UI-компонентов в контексте реального приложения сопряжена с практическими ограничениями: чтобы увидеть компонент в определённом состоянии, разработчику необходимо воспроизвести его через реальные взаимодействия — авторизоваться, создать объект, навигировать к нужной странице. Это замедляет итерации при работе над внешним видом и поведением компонентов.

**Storybook** решает эту проблему: инструмент предоставляет изолированную среду, в которой каждый компонент отображается независимо с произвольно заданными входными данными. Каждое такое представление называется **story** — именованное зафиксированное состояние компонента. Набор stories служит одновременно живой документацией, средой тестирования и инструментом демонстрации.

В проекте используется связка **`@storybook/vue3-vite`** — официальный фреймворк Storybook для Vue 3 с интеграцией через Vite, что обеспечивает использование общего `vite.config.ts` и алиасов без дополнительной настройки.

### 5.3.2 Конфигурация и среда выполнения

Файл `.storybook/preview.ts` инициализирует глобальные провайдеры через `setup()` — аналог `app.use()` в `main.ts` реального приложения:

```typescript
setup((app) => {
  app.use(createPinia())
  app.use(storybookRouter) // createMemoryHistory — без реального URL
  app.use(i18n)
  app.use(VueQueryPlugin)
  app.use(PrimeVue, { theme: primeVueThemeConfig })
  app.use(ToastService)
})
```

Vue Router инициализируется с `createMemoryHistory()` вместо `createWebHistory()` — история маршрутов хранится в памяти, что корректно работает в изолированной среде Storybook. Дополнительно подключаются глобальные стили: CSS reset и файл `tokens.css` с дизайн-токенами (`--color-primary`, `--surface-card` и др.), без которых компоненты отображались бы без тематического оформления.

На уровне всех stories применяется декоратор `withAppSurface`, воспроизводящий фоновый цвет и типографику реального приложения:

```typescript
export const withAppSurface: Decorator = () => ({
  template: `
    <div style="
      padding: 1.5rem;
      background: var(--surface-ground);
      color: var(--text-color);
      font-family: var(--font-family);
    ">
      <story />
    </div>
  `
})
```

Декораторы расположены в `src/shared/lib/storybook/decorators.ts` в соответствии с принципами FSD — общие утилиты разработки находятся внутри `src/`.

### 5.3.4 Interaction tests и проверка доступности

Storybook поддерживает **interaction tests** — программные сценарии взаимодействия с компонентом в поле `play` story. Функция `play` выполняется автоматически после монтирования:

```typescript
export const InteractionTest: Story = {
  name: 'Interaction: aria-label по теме',
  play: async ({ canvasElement }) => {
    const canvas = within(canvasElement)
    const button = canvas.getByRole('button')
    await expect(button).toBeVisible()

    const label = button.getAttribute('aria-label')
    await expect(['Тёмная тема', 'Светлая тема', 'Dark mode', 'Light mode']).toContain(label)
  }
}
```

`getByRole('button')` находит элемент по ARIA-роли — это делает тест устойчивым к изменениям HTML-структуры компонента. Interaction tests запускаются тремя способами: в браузере Storybook через панель «Interactions», через Vitest + `@storybook/addon-vitest` (`npm run test:storybook`) и в CI как часть пайплайна.

Аддон `@storybook/addon-a11y` интегрирует библиотеку `axe-core` для автоматической проверки доступности каждой открытой story. На момент написания работы для всех 6 компонентов нарушения в категории «Violations» отсутствуют.

### 5.4.5 Эффективность системы автоматических проверок

Внедрение многоуровневой системы тестирования и автоматизации обеспечивает следующий совокупный эффект:

**Раннее обнаружение ошибок.** Статический анализ и Vitest-тесты выполняются непосредственно в цикле разработки — до попадания кода в общую ветку. Время между появлением ошибки и её обнаружением измеряется секундами, а не часами.

**Защита от регрессий.** Тесты маппер, схем валидации и бизнес-логики фиксируют ожидаемое поведение. При рефакторинге или изменении требований любое непреднамеренное изменение поведения немедленно выявляется упавшим тестом.

**Единый стандарт кода.** Автоматическое форматирование и линтинг через `lint-staged` исключают дискуссии о стиле кода на code review. Все файлы в репозитории соответствуют единым правилам Prettier и ESLint вне зависимости от IDE разработчика.

**Живая документация.** 43 Storybook-истории для 21 компонента служат актуальной документацией компонентного API — в отличие от текстовой документации, они не устаревают, поскольку генерируются непосредственно из кода компонентов.
