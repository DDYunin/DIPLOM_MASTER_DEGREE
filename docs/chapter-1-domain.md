# 1 Изучение предметной области и анализ требований к LMS-платформам

## 1.1 Анализ предметной области: структура и участники учебного процесса в высшем учебном заведении

Проектирование клиентской части образовательной платформы требует предварительной формализации предметной области — перевода реальных объектов и процессов академической среды в строгие термины программной инженерии. Без такой формализации невозможно построить согласованную модель данных, определить структуру навигации и корректно описать поведение интерфейса в различных состояниях системы.

В основе подхода лежит концепция Ubiquitous Language [Evans, 2003]: единый понятийный словарь, разделяемый аналитиками, разработчиками и предметными экспертами, устраняет семантический разрыв между бизнес-процессами вуза и их программными абстракциями. Настоящий раздел решает три взаимосвязанные задачи: формирует глоссарий ключевых сущностей, описывает их организационные связи и определяет жизненный цикл динамических процессов, которые клиентское приложение должно визуализировать.

### 1.1.1 Терминологический глоссарий предметной области

В рамках автоматизируемой образовательной среды ключевые сущности учебного процесса формализуются следующим образом.

**Пользователь (User)** — субъект системы, обладающий уникальными учётными данными для входа (login/password) и назначенной ролью, которая определяет набор доступных интерфейсов и операций. Система поддерживает три основные роли: Администратор, Преподаватель и Студент.

**Роль (Role)** — именованный набор разрешений, закреплённый за пользователем. На уровне клиентского приложения роль управляет видимостью компонентов навигации, доступностью маршрутов (Navigation Guards) и составом отображаемых элементов управления. Проверка роли осуществляется на клиенте на основе декодирования JWT-токена, полученного при аутентификации.

**Электронный учебный курс (Course)** — структурированная единица образовательного контента, выступающая в роли контейнера для учебных материалов, метаданных и пользователей. На уровне клиентского приложения курс представляется в виде иерархического дерева тем и элементов с возможностью перехода между разделами без перезагрузки страницы.

**Элемент курса (Course Element)** — минимальная неделимая единица учебного контента. Сущность полиморфна: на клиенте реализуются типы «текстовая лекция», «видеоматериал», «PDF-документ», «презентация», «тест» и «практическое задание», каждый из которых требует собственного компонента отображения.

**Банк вопросов (Question Bank)** — изолированное логическое хранилище тестовых и контрольных заданий, категорированных по темам, уровням сложности и типам ответов. Используется преподавателем для статической или динамической сборки тестов. Архитектурная изолированность банка позволяет переиспользовать вопросы в нескольких тестах без дублирования.

**Тест (Assessment)** — контрольное мероприятие, собранное из вопросов банка. Тест обладает набором параметров прохождения: ограничение по времени, срок сдачи, проходной балл. На клиенте тест порождает сессию прохождения.

**Сессия тестирования (Assessment Session)** — временное состояние, возникающее в момент начала прохождения теста студентом. Сессия хранит: идентификатор студента, снимок вопросов, текущие ответы, оставшееся время и статус завершения. Промежуточные ответы периодически автосохраняются на сервер для предотвращения потери прогресса при сетевых сбоях.

**Оценка (Grade)** — количественный результат прохождения теста или выполнения задания. Для тестов с выбором ответа оценка вычисляется автоматически сервером; для заданий со свободным ответом требует ручной проверки преподавателем.

**Балльно-рейтинговая система (БРС)** — накопительная модель оценки успеваемости, агрегирующая оценки за все элементы курса в итоговый рейтинг студента. Требует от клиентского интерфейса динамических аналитических дашбордов и интерактивных ведомостей для преподавателей.

**Академическая группа (Academic Group)** — совокупность пользователей с ролью «Студент», объединённых общим годом поступления и направлением подготовки. Закрепление группы за курсом определяет, для каких студентов курс будет отображаться в их личных кабинетах.

### 1.1.2 Организационно-структурная модель и её отображение в SPA-архитектуре

Организационная структура университета имеет строго иерархический характер. С точки зрения информационного моделирования вложенность сущностей вуза описывается следующей цепочкой:

> Университет → Институт / Факультет → Кафедра → Направление подготовки → Академическая группа → Студент

Данная иерархия напрямую проецируется на архитектуру Single Page Application, определяя структуру клиентского роутинга и интерфейсные паттерны.

**Динамический клиентский роутинг (Routing).** Иерархия вуза задаёт вложенную структуру динамических маршрутов в менеджере маршрутов. Каждый уровень иерархии соответствует сегменту URL с параметром-идентификатором, что позволяет компонентам страниц извлекать нужный идентификатор из параметров маршрута и выполнять соответствующий API-запрос без передачи данных через глобальное хранилище.

**Древовидные компоненты интерфейса (Tree Views).** Для визуализации иерархии в административной панели применяются интерактивные древовидные компоненты. Они позволяют администратору наглядно воспринимать связи между кафедрами, направлениями и группами, а также выполнять операции добавления, перемещения или удаления узлов в рамках единого экрана, не переключаясь между страницами.

**Каскадный выбор (Cascade Selects).** При создании учётных записей или закреплении преподавателей за структурными подразделениями используются каскадные выпадающие списки. Клиентское приложение динамически фильтрует список дочерних элементов при выборе родительского: выбор института ограничивает список кафедр, выбор кафедры — список направлений. Это снижает вероятность ошибок ввода и уменьшает число запросов к серверу.

**Изолированные порталы по ролям.** Каждая роль пользователя обслуживается собственным набором маршрутов, защищённых Navigation Guards. Попытка перехода к маршруту другой роли вызывает автоматическое перенаправление. Такая изоляция делает порталы независимыми модулями, развиваемыми параллельно.

### 1.1.3 Жизненный цикл и состояния ключевых сущностей

Учебный процесс представляет собой совокупность динамических процессов. Для обеспечения корректного поведения интерфейса состояния ключевых сущностей описываются в виде конечных автоматов: текущее состояние управляет доступностью элементов управления и логикой отображения данных.

**Состояния курса:**

- **Черновик (Draft)** — начальное состояние при создании. Курс доступен для редактирования преподавателю, но полностью скрыт от студентов.
- **Активный (Active)** — курс опубликован. Отображается на дашборде студентов прикреплённых групп, открывается доступ к материалам и тестам.
- **Архивный (Archived)** — курс завершён. Для студентов переходит в режим «только чтение», убирается с главного дашборда и перемещается в раздел истории.

**Состояния задания (практической работы):**

- **Не начато (Not Started)** — задание доступно, кнопка отправки активна.
- **В процессе (In Progress)** — студент сохранил черновик ответа.
- **На проверке (Pending Review)** — решение отправлено. У студента блокируется повторная отправка; у преподавателя запись подсвечивается как требующая проверки.
- **Проверено (Graded)** — преподаватель выставил оценку и оставил комментарий. Редактирование заблокировано для обеих сторон.

**Состояния тестовой сессии:**

- **Доступен (Available)** — тест опубликован, кнопка запуска активна.
- **Выполняется (In Session)** — студент запустил тест. Активирован таймер обратного отсчёта; промежуточные ответы периодически автосохраняются.
- **Завершён (Submitted)** — время вышло или студент нажал «Завершить». Данные отправлены на сервер, запускается автоматическая проверка.
- **Оценён (Graded)** — результаты доступны студенту.

Формализация конечных автоматов на ранних этапах проектирования позволяет определить полный набор состояний, которые компоненты интерфейса должны обрабатывать явно, предотвращая ситуации неопределённого UI-состояния при нештатных переходах.

## 1.2 Обзор и сравнительный анализ существующих систем управления обучением (LMS)

Для обоснованного выбора архитектурных решений и интерфейсных паттернов необходимо провести критический анализ существующих систем управления обучением. Среди платформ, широко применяемых в академической среде, наибольший интерес представляют четыре системы: Moodle, Canvas LMS, Open edX и Stepik. Они охватывают спектр от классических монолитных решений с открытым исходным кодом до современных высоконагруженных облачных SaaS-платформ.

### Moodle

Moodle (Modular Object-Oriented Dynamic Learning Environment) — наиболее распространённая платформа в российских вузах. Это монолитная система с открытым исходным кодом, написанная на PHP. Главное достоинство Moodle — развитая экосистема плагинов и глубокая проработка академических сценариев: ведение журналов, учёт групп и иерархических структур вуза, интеграция с деканатом.

Однако с точки зрения фронтенд-архитектуры Moodle имеет существенные недостатки. Система использует классический серверный рендеринг на основе шаблонизатора Mustache и устаревших JS-библиотек (jQuery, RequireJS). Это приводит к полной перезагрузке страницы при каждом переходе, медленному отклику интерфейса и перегруженному DOM-дереву. Реализация плавных анимаций и интерактивного тестирования в реальном времени в рамках такой архитектуры сопряжена со значительными трудозатратами.

**Ценный опыт:** детальная ролевая модель и полнофункциональная поддержка иерархических структур вуза (факультет → кафедра → группа → студент).

### Canvas LMS

Canvas LMS от компании Instructure построен на базе Ruby on Rails и использует React в качестве фронтенд-стека. Платформа предлагает более отзывчивый и визуально чистый интерфейс по сравнению с Moodle: часть экранов реализована как React SPA внутри монолитного приложения.

Тем не менее клиентская часть Canvas глубоко интегрирована в серверный монолит, что усложняет кастомизацию. Самостоятельное развёртывание Canvas LMS представляет собой сложную инженерную задачу из-за жёсткой привязки к облачной инфраструктуре AWS. Платформа ориентирована на западный SaaS-рынок и слабо поддерживает особенности российской академической среды.

**Ценный опыт:** применение компонентного подхода на базе React для отдельных интерактивных экранов; концепция «модули → задания → баллы», аналогичная требуемой БРС.

### Open edX

Open edX — открытая платформа, созданная MIT и Harvard и широко используемая как для корпоративного, так и для академического обучения. Бэкенд построен на Python (Django), фронтенд активно переводится с серверного рендеринга на микрофронтенд-архитектуру (React + Webpack Module Federation).

Open edX обеспечивает богатую систему типов учебного контента (видео, тесты, задачи с вводом кода, интерактивные задания) и имеет хорошо документированный REST API. Однако полноценное развёртывание и настройка платформы требуют глубокой DevOps-экспертизы: стек включает Celery, Redis, MySQL и MongoDB одновременно. Административный интерфейс управления структурой вуза в Open edX отсутствует в стандартной комплектации.

**Ценный опыт:** концепция изолированных модульных компонентов для разных типов контента; паттерн автосохранения ответов теста с возможностью возобновления сессии.

### Stepik

Stepik — современная российская облачная платформа, ориентированная на интерактивные курсы и автоматическую проверку задач. Клиентская часть реализована как высокопроизводительное SPA на базе React. Stepik демонстрирует эталонный пользовательский опыт: мгновенные переходы между страницами, плавно работающий таймер тестов, удобный конструктор шагов курса.

Принципиальное ограничение — исключительно SaaS-модель без возможности развёртывания на серверах университета (on-premise), что исключает интеграцию с внутренними базами данных вуза и соответствие требованиям законодательства о персональных данных. Кроме того, в Stepik отсутствуют инструменты администрирования сложной вузовской структуры (кафедры, направления, закреплённые академические группы).

**Ценный опыт:** SPA-архитектура клиента с мгновенной навигацией; продуманный дизайн интерфейса прохождения теста с картой вопросов и таймером.

### Выводы и заимствованные практики

Проведённый анализ позволяет выделить четыре направления лучших практик, которые служат ориентирами при проектировании разрабатываемой платформы.

**1. SPA-архитектура клиента** (опыт Stepik, Open edX). Все сценарии взаимодействия, требующие высокой отзывчивости — прохождение теста, редактирование содержания курса, навигация по структуре — реализуются на клиенте без полной перезагрузки страницы. Vue Router обеспечивает мгновенные переходы между экранами внутри одного SPA.

**2. Глубокая ролевая модель и поддержка иерархии вуза** (опыт Moodle). Система учитывает реальную структуру российского вуза: университет → институт → кафедра → направление → группа → студент. Закрепление пользователей за структурными подразделениями определяет область видимости контента в интерфейсе каждой роли.

**3. Изолированные компоненты для типов контента** (опыт Open edX, Canvas). Каждый тип элемента курса (видео, PDF, тест, задание) реализуется как самостоятельный полиморфный компонент с собственной логикой отображения, не зависящей от соседних типов.

**4. Надёжная сессия тестирования с автосохранением** (опыт Stepik, Open edX). Промежуточные ответы студента автоматически сохраняются на сервер по мере заполнения. При случайном закрытии вкладки или сетевом сбое сессия восстанавливается с последнего сохранённого состояния.

При этом цель данной работы не состоит в создании прямой альтернативы перечисленным коммерческим и академическим решениям. Основная научно-практическая задача заключается в прохождении полного жизненного цикла разработки сложной образовательной веб-платформы с применением современного технологического стека и методологий: Vue 3 в сочетании с Feature-Sliced Design обеспечивает такую декомпозицию кодовой базы, при которой добавление новых функциональных модулей не нарушает целостности существующей архитектуры.

## 1.4 Разработка функциональных требований к клиентской части платформы

Функциональные требования определяют то, какие возможности должна предоставлять система пользователям. В ходе анализа были формализованы и систематизированы функциональные требования для трёх ключевых ролей пользователей: Администратора, Преподавателя и Студента.

### Общие функциональные требования

Перед началом работы с платформой клиентская часть должна обеспечивать прохождение сквозных процедур, обязательных для всех категорий пользователей:

- **Идентификация и аутентификация:** каждый пользователь системы должен проходить процедуру авторизации с помощью пары уникального логина и пароля.
- **Разграничение прав доступа:** после успешного входа система определяет назначенную роль пользователя и на клиентском уровне динамически формирует доступный набор интерфейсов, меню навигации и защищённых маршрутов.
- **Сброс и восстановление пароля:** клиентская часть должна содержать сценарий самостоятельного восстановления пароля пользователем через указание электронной почты, связанной с учётной записью, и последующее подтверждение изменений.

### Функциональные требования к интерфейсу Администратора

Интерфейс Администратора ориентирован на техническое обеспечение работоспособности системы, управление иерархической структурой вуза и ведение базы данных пользователей:

- **Управление учётными записями пользователей:** Администратор должен иметь возможность создавать новые учётные записи (как вручную для единичных пользователей, так и пакетно посредством импорта файлов в формате Excel), редактировать существующие профили и удалять неактуальные аккаунты.
- **Управление иерархической структурой университета:** интерфейс должен предоставлять инструменты для визуального редактирования древовидной структуры направлений подготовки, институтов/факультетов, кафедр и академических групп.
- **Управление правами доступа преподавателей:** Администратор закрепляет за конкретным преподавателем список доступных ему учебных направлений, институтов или групп, определяя его зону ответственности в системе.

### Функциональные требования к интерфейсу Преподавателя

Интерфейс Преподавателя предназначен для создания учебного контента, контроля успеваемости студентов и управления учебными курсами:

- **Управление курсами:** возможность создания новых курсов с указанием названия, описания и закреплённых академических групп. Преподаватель может переводить курсы в архивный статус и добавлять других преподавателей в качестве соавторов.
- **Конструирование содержания:** интерфейс позволяет выстраивать структуру курса и наполнять её учебными материалами разных форматов (текст, презентации, PDF-документы, видеофайлы).
- **Управление банком вопросов:** создание и ведение централизованной базы вопросов различных типов (тестовые с одиночным или множественным выбором, контрольные со свободным кратким или развёрнутым ответом).
- **Создание тестов и контрольных заданий:** сборка тестов из готовых банков вопросов, установка проходного балла, ограничения по времени и жёстких сроков сдачи.
- **Мониторинг успеваемости студентов:** детальная статистика по курсу в виде интерактивных графиков и таблиц с возможностью экспорта в Excel.
- **Проверка работ:** удобный инструмент для ручной проверки развёрнутых ответов студентов с возможностью выставления оценки и отправки текстового комментария.

### Функциональные требования к интерфейсу Студента

Интерфейс Студента представляет собой адаптивное рабочее пространство, спроектированное для максимально комфортного прохождения обучения:

- **Дашборд доступных курсов:** Студент должен видеть наглядный перечень всех учебных курсов, на которые он записан.
- **Взаимодействие с учебным материалом:** навигация по структуре курса, последовательное чтение лекций, просмотр видео, предпросмотр и скачивание методических материалов.
- **Прохождение тестовых работ:** интерактивное выполнение тестов с визуальным отображением оставшегося времени и отправка решений практических заданий.
- **Мониторинг успеваемости:** доступ к собственным оценкам по всем элементам курса, обратной связи от преподавателей и общему индикатору прогресса.

## 1.5 Разработка нефункциональных требований

Нефункциональные требования определяют качественные характеристики клиентской части платформы. Специфика разработки клиентского SPA-приложения для академической среды обуславливает следующие нефункциональные требования.

### Требования к интерфейсу пользователя

- **Интуитивность:** интерфейс должен быть понятным для пользователей с разным уровнем компьютерной грамотности. Навигация строится по принципу минимального количества кликов для достижения целевого действия.
- **Кроссплатформенная адаптивность:** клиентская часть должна корректно отображаться и сохранять полную функциональность на персональных компьютерах, ноутбуках и планшетах.
- **Доступность:** обязательна поддержка стандартов доступности (контрастные цветовые схемы, масштабирование текста без разрушения вёрстки, поддержка навигации с клавиатуры).

### Производительность и оптимизация

- **Время первичной загрузки:** размер исходного бандла приложения минимизируется за счёт разделения кода и ленивой загрузки некритичных модулей. Время до первой отрисовки контента (FCP) при стандартном интернет-соединении должно составлять не более 1,5–2 секунд.
- **Отзывчивость интерфейса:** переходы между страницами внутри SPA должны происходить плавно, без визуального мерцания. Для сглаживания времени ожидания ответов от сервера используются анимированные скелетоны.
- **Управление состоянием:** хранение глобального состояния приложения должно исключать лишние повторные сетевые запросы при переключении между вкладками или возврате на предыдущие страницы.

### Безопасность и разграничение доступа

- **Защита каналов связи:** весь обмен данными осуществляется по защищённому протоколу HTTPS.
- **Безопасное хранение сессий:** авторизационные токены (JWT) хранятся в защищённых клиентских хранилищах, минимизирующих риски XSS-атак.
- **Строгая изоляция данных:** на клиентском уровне заблокирована возможность просмотра данных, не принадлежащих текущему пользователю. Изменение персональных данных и иерархии вуза недоступно в интерфейсах Преподавателя и Студента.

### Надёжность и отказоустойчивость

- **Обработка сетевых ошибок:** в случае обрыва связи клиентская часть выводит понятные пользователю предупреждения, предотвращая зависание интерфейса или потерю введённых данных.
- **Автоматическое сохранение прогресса:** при прохождении тестирования промежуточные ответы студента автоматически сохраняются, чтобы в случае сбоя студент мог продолжить выполнение задания с того же места.

## 1.6 Проектирование и описание пользовательских сценариев

Для детальной спецификации функциональных требований и последующего проектирования интерфейсов необходимо формализовать основные сценарии взаимодействия пользователей с платформой. Каждый сценарий описывает последовательность действий актора и реакцию системы.

### 1.6.1 Сценарии взаимодействия для роли «Администратор»

**Сценарий 1.6.1.1: Ручное создание учётной записи пользователя**

- **Предусловия:** Администратор авторизован в системе и находится в административной панели.
- **Основной сценарий:**
  1. Администратор переходит на страницу «Управление пользователями».
  2. Нажимает кнопку «Создать пользователя».
  3. Заполняет форму (ФИО, логин, email, выбор роли).
  4. Нажимает кнопку «Сохранить».
- **Результат:** Данные отправляются на сервер, создаётся запись в базе данных, клиентская часть отображает уведомление об успешном создании.

**Сценарий 1.6.1.2: Импорт учётных записей из внешнего файла**

- **Предусловия:** Администратор подготовил файл со списком пользователей в формате Excel.
- **Основной сценарий:**
  1. Администратор переходит в раздел «Управление пользователями».
  2. Нажимает кнопку «Импортировать из файла».
  3. В диалоговом окне выбирает файл и нажимает «Загрузить».
  4. Подтверждает действие нажатием кнопки «Импортировать».
- **Результат:** Пакет данных отправляется на сервер, регистрируются новые пользователи, интерфейс выводит отчёт об успешном импорте.

**Сценарий 1.6.1.3: Модификация организационной структуры вуза**

- **Предусловия:** Администратор находится в разделе «Иерархия структуры».
- **Основной сценарий:**
  1. Администратор просматривает древовидную структуру направлений, институтов и групп.
  2. Выбирает узел дерева и нажимает «Добавить дочерний элемент» или «Редактировать».
  3. Вводит название и сохраняет изменения.
- **Результат:** Дерево структуры динамически обновляется на клиенте, обновлённая конфигурация отправляется на сервер.

**Сценарий 1.6.1.4: Просмотр и редактирование профиля пользователя**

- **Предусловия:** Пользователь зарегистрирован в системе.
- **Основной сценарий:**
  1. Администратор переходит на страницу «Пользователи».
  2. Использует фильтры и поиск для нахождения нужного человека.
  3. Кликает на имя пользователя для открытия карточки профиля.
  4. Вносит изменения и нажимает «Сохранить изменения».
- **Результат:** Обновлённая информация отправляется на сервер, локальный стейт обновляется, выводится уведомление об успешном сохранении.

### 1.6.2 Сценарии взаимодействия для роли «Преподаватель»

**Сценарий 1.6.2.1: Создание учебного курса**

- **Предусловия:** Преподаватель авторизован в системе.
- **Основной сценарий:**
  1. На главной странице нажимает кнопку «Добавить курс».
  2. Вводит название и описание курса.
  3. При необходимости указывает соавторов.
  4. Нажимает «Сохранить изменения».
- **Результат:** Курс создаётся и становится доступным для редактирования в личном кабинете преподавателя.

**Сценарий 1.6.2.2: Структурирование содержания курса**

- **Предусловия:** Учебный курс успешно создан.
- **Основной сценарий:**
  1. Преподаватель переходит в раздел «Содержание курса».
  2. Нажимает кнопку добавления новой темы.
  3. Внутри созданной темы нажимает «Добавить подтему».
  4. Нажимает «Сохранить изменения».
- **Результат:** На клиенте формируется иерархическая структура курса, готовая к наполнению материалами.

**Сценарий 1.6.2.3: Добавление учебных материалов в курс**

- **Предусловия:** Структура курса сформирована.
- **Основной сценарий:**
  1. Преподаватель выбирает нужную подтему в структуре курса.
  2. Нажимает «Добавить материал».
  3. Выбирает тип материала и загружает его в систему.
  4. Указывает название и описание, нажимает «Сохранить».
- **Результат:** Материал прикрепляется к подтеме курса и становится доступен студентам.

**Сценарий 1.6.2.4: Добавление вопросов в банк вопросов**

- **Предусловия:** Преподаватель находится в разделе «Банк вопросов».
- **Основной сценарий:**
  1. Выбирает существующий банк или создаёт новый.
  2. Нажимает «Добавить вопрос».
  3. Определяет тип вопроса, заполняет текст и указывает сложность.
  4. Для тестового вопроса добавляет варианты ответов и отмечает правильные.
  5. Нажимает «Сохранить вопрос».
- **Результат:** Вопрос сохраняется в базе данных банка и готов к использованию в тестах.

**Сценарий 1.6.2.5: Создание теста на основе банка вопросов**

- **Предусловия:** Создана подтема курса, сформирован и наполнен банк вопросов.
- **Основной сценарий:**
  1. Преподаватель переходит в нужную подтему и нажимает «Добавить тест».
  2. Вводит название, описание и параметры прохождения.
  3. Во вкладке «Вопросы» выбирает вопросы из банка.
  4. Настраивает баллы за каждый ответ и нажимает «Сохранить тест».
- **Результат:** Тест публикуется в структуре курса и становится доступен студентам.

**Сценарий 1.6.2.6: Проверка контрольных заданий студентов**

- **Предусловия:** Студенты выполнили контрольные работы, требующие ручной оценки.
- **Основной сценарий:**
  1. Преподаватель переходит в раздел статистики курса.
  2. Выбирает задание из списка требующих проверки.
  3. Просматривает прикреплённые файлы решений.
  4. Выставляет оценку и при необходимости пишет комментарий.
  5. Нажимает «Сохранить оценки».
- **Результат:** Оценки фиксируются в системе, студент получает уведомление, ведомость пересчитывается.

**Сценарий 1.6.2.7: Отслеживание успеваемости и экспорт отчётов**

- **Предусловия:** Студенты начали прохождение курса.
- **Основной сценарий:**
  1. Преподаватель переходит в раздел статистики курса.
  2. Выбирает академическую группу или конкретного студента.
  3. Изучает сводный прогресс и результаты тестов.
  4. Нажимает «Экспорт» и выбирает формат файла (CSV или Excel).
- **Результат:** На устройство скачивается файл с актуальными данными об успеваемости.

**Сценарий 1.6.2.8: Назначение учебных групп на курс**

- **Предусловия:** Курс создан, Администратор назначил преподавателя на соответствующие группы.
- **Основной сценарий:**
  1. Преподаватель заходит в настройки нужного курса.
  2. Переходит во вкладку «Доступ групп».
  3. Отмечает группы, для которых открывается данный курс.
  4. Нажимает «Сохранить изменения».
- **Результат:** Курс появляется в личных кабинетах всех студентов выбранных академических групп.

### 1.6.3 Сценарии взаимодействия для роли «Студент»

**Сценарий 1.6.3.1: Прохождение разделов учебного курса**

- **Предусловия:** Студент авторизован на платформе и записан на курс.
- **Основной сценарий:**
  1. Студент открывает список своих курсов и переходит на нужный курс.
  2. Система выводит структуру доступных материалов.
  3. Студент выбирает лекцию или практический материал.
  4. В зависимости от типа контента изучает текст, просматривает видео или скачивает PDF.
  5. Использует навигацию для перехода к следующей теме.
- **Результат:** В системе фиксируется факт изучения темы, прогресс прохождения курса увеличивается.

**Сценарий 1.6.3.2: Прохождение тестовой работы**

- **Предусловия:** Студенту доступен опубликованный в курсе тест.
- **Основной сценарий:**
  1. Студент выбирает активный тест в списке материалов курса.
  2. Ознакомляется с параметрами и нажимает кнопку начала тестирования.
  3. Последовательно отвечает на вопросы, контролируя оставшееся время по таймеру.
  4. Нажимает кнопку «Завершить тест».
- **Результат:** Система фиксирует ответы, отправляет их на проверку и выводит набранные баллы.
