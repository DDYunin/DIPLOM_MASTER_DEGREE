### Слайд 7 — Архитектурное решение: Feature-Sliced Design

**Заголовок:** Архитектурная методология Feature-Sliced Design

**Проблема традиционного подхода:**

- Папки `components/`, `stores/`, `api/` — «свалка» при росте проекта
- Круговые зависимости, размытая ответственность, конфликты в Git при совместной работе

**Решение — FSD: 6 слоёв с однонаправленными зависимостями (сверху вниз):**

```
app → pages → widgets → features → entities → shared
```

**Ключевые принципы:**

- **Публичный API (index.ts)** — каждый модуль экспортирует только то, что разрешено
- **Низкая связанность** — запрет на перекрёстные импорты между слайсами одного слоя
- **Высокое зацепление** — весь код одной фичи (UI, API, стейт) в одном слайсе

### [→ Слайд 7 — Feature-Sliced Design] (~1 мин 30 сек)

Ключевым архитектурным решением стал выбор методологии **Feature-Sliced Design**.

Традиционный подход — разбивать проект по техническому типу файлов: отдельные папки `components`, `stores`, `api`. На небольших проектах это работает, но при росте команды и функционала папки превращаются в «свалку» из сотен несвязанных файлов. Любое изменение в одной фиче затрагивает файлы по всему проекту, возникают круговые зависимости, а у новых разработчиков нет способа понять, что от чего зависит.

FSD решает эту проблему через **строгую послойную декомпозицию**. Шесть слоёв выстроены в вертикальную иерархию: `shared → entities → features → widgets → pages → app`. Код верхних слоёв может использовать нижние, но не наоборот. Слайсы на одном слое не знают друг о друге.

Это даёт три важных свойства. **Публичный API**: каждый модуль явно объявляет, что он экспортирует. **Низкая связанность**: изменение интерфейса студента гарантированно не затронет интерфейс преподавателя. **Высокое зацепление**: весь код одной бизнес-фичи — UI, запросы к API, состояние — сосредоточен в одном слайсе, что упрощает навигацию и командную разработку.

### [→ Слайд 9 — Аутентификация] (~30 сек)

Система аутентификации реализована на основе JWT. После входа клиент получает access и refresh токены. При истечении срока действия access-токена он автоматически обновляется без участия пользователя.

Роль пользователя извлекается из токена и используется **Navigation Guards** во Vue Router: каждый маршрут защищён, а при попытке перейти в чужой портал — выполняется автоматический редирект.

### [→ Слайд 10 — Портал Администратора] (~40 сек)

Интерфейс администратора включает три основных модуля.

Первый — **визуальный редактор иерархии вуза**: интерактивное дерево, в котором можно добавлять, редактировать и удалять узлы структуры прямо на странице.

Второй — **управление пользователями**: поиск, фильтрация по роли, редактирование профилей. Для массового создания аккаунтов реализован импорт из Excel-файла.

Третий — **разграничение прав преподавателей**: администратор привязывает каждого преподавателя к конкретным институтам, направлениям и группам, что определяет его зону видимости в системе.

Портал преподавателя — наиболее функционально насыщенный.

**Конструктор курсов** позволяет выстраивать иерархическую структуру тем и наполнять их материалами различных форматов. К курсу привязываются академические группы — именно им он становится виден.

**Банк вопросов и конструктор тестов** поддерживают вопросы с выбором ответа и со свободным вводом. При создании теста задаются лимит времени, проходной балл и дедлайн.

**Раздел статистики** отображает интерактивные графики прогресса по группам и отдельным студентам. Ведомость успеваемости можно экспортировать в Excel.

### [→ Слайд 12 — Портал Студента] (~40 сек)

Интерфейс студента спроектирован для максимально комфортного и сфокусированного прохождения обучения.

На главной странице — **дашборд курсов** с индикатором прогресса по каждому. Внутри курса студент последовательно изучает материалы, смотрит видео, скачивает PDF и презентации.

**Модуль тестирования** отображает вопросы, карту ответов и таймер обратного отсчёта. После завершения — мгновенный результат.

В разделе успеваемости студент видит все свои оценки, комментарии преподавателя и общий прогресс прохождения программы.

### [→ Слайд 13 — Обеспечение качества] (~45 сек)

Система обеспечения качества выстроена на трёх уровнях.

**Первый уровень** — статический анализ, интегрированный в процесс коммита. Husky и lint-staged запускают ESLint и Prettier автоматически — коммит с ошибками просто не проходит.

**Второй уровень** — автоматическое тестирование на Vitest. Покрыты unit-тестами функции трансформации данных и маппинг DTO; интеграционными — Zod-схемы валидации и сервисы; компонентными — поведение UI-компонентов через Vue Test Utils.

**Третий уровень** — Storybook. Для компонентов всех трёх порталов написаны story-файлы с автодокументацией и interaction-тестами. Аддон a11y автоматически проверяет каждый компонент по критериям WCAG 2.1. На момент написания работы количество нарушений в категории Violations равно нулю.

## СПРАВОЧНАЯ ИНФОРМАЦИЯ

### Возможные вопросы комиссии и краткие ответы

**Q: Почему Vue 3, а не React?**
Vue 3 с Composition API предоставляет схожие возможности реактивности, при этом имеет более низкий порог входа и встроенный механизм реактивности без дополнительных хуков. FSD одинаково применим к обоим фреймворкам — выбор Vue обусловлен личным опытом и исследованием производительности в контексте задачи.

**Q: Чем FSD лучше обычной доменно-модульной структуры?**
Доменно-модульный подход группирует код по бизнес-доменам, но не регламентирует направление зависимостей. FSD добавляет вертикальную иерархию слоёв, запрещая перекрёстные импорты между слайсами одного слоя. Это устраняет круговые зависимости и делает последствия любых изменений предсказуемыми.

**Q: Как организована связь с бэкендом?**
Все HTTP-запросы выполняются через единый API-клиент в слое `shared/api`. Кэширование ответов и синхронизация состояния с сервером управляются TanStack Query. Это позволяет не дублировать запросы при переходе между страницами и реализовать оптимистичные обновления.

**Q: Как тестировалось приложение при отсутствии готового бэкенда?**
Для разработки и тестирования клиентской части использовался json-server — инструмент, генерирующий REST API из JSON-файла. Это позволило вести разработку и писать тесты независимо от готовности серверной части.

**Q: Какое покрытие кода тестами?**
В работе не ставилась цель достичь формального процента покрытия. Тестами покрыты наиболее критичные функции: трансформации DTO (маппинг данных между серверными и клиентскими моделями), схемы валидации Zod и поведение ключевых компонентов. Такой подход соответствует принципу тестирования наиболее рискованных участков кода.
